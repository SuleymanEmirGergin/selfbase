# selfbase v2 — Wave 2 (CLI, functions and database features) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (chosen by the owner) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a selfbase project usable for an app team's daily work: a `selfbase` CLI that reads an unchanged `supabase/` folder (migrations, functions, secrets, types, config, local stack), function deploys with per-function isolation and logs, the database features of spec 8.4, external Postgres access over TLS, and the Studio screens for all of it.

**Architecture:** Every server-side operation is a control-plane API action first (`/v1` when the Management API has the operation, `/platform` otherwise); the CLI and Studio are clients of it. Control forwards in-database and volume work to the project's `core:8081` admin API; `core` owns migration apply, the type generator, catalog reads and the functions volume, `fn` runs each function in its own Deno Worker from a manifest on that volume. Database features arrive in existing projects through platform migrations `0004`–`0008` and a new db image.

**Tech Stack:** as wave 1 (Node 24 + TypeScript, Hono, `pg`, React 19 + Vite, Postgres 17, PostgREST 14.1, PgBouncer, Deno 2, vitest, Playwright), plus: `esbuild` and `smol-toml` (CLI bundle), `@peculiar/x509` (control's internal CA), `graphiql` (Studio, lazy chunk), pg_graphql and pg_jsonschema (pgrx build in the db image), pgmq (SQL files), migra (local one-shot image built by the CLI).

**Spec:** `docs/superpowers/specs/2026-11-22-selfbase-v2-design.md` (binding). Every implementer reads sections 3–5, 7.4–7.9, 8.4–8.6, 8.9, 11 (wave 2) and 15, plus the sections their task names. Wave 1 plan, for conventions and what exists: `docs/superpowers/plans/2026-11-22-selfbase-v2-wave1.md`.

## Execution

- Subagent-driven: one implementer per task, a task review after each. The whole-branch review runs after Task 24, before anything is pushed or deployed.

- **Owner step** lines need the owner at that moment. A builder never works around one. Server tasks (25, 26) are run by one builder over SSH, never in parallel.
- **Depends on wave 1 deploy:** lines mark what is assumed about the still-running wave 1 deploy and cutover (wave 1 Tasks 20–24). Task 1 replaces each assumption with the measured fact, or stops.

## Global Constraints

- No `supabase/*` image and no `@supabase/*` package at runtime. The product never shows the Supabase name or logo; "works with supabase-js" is allowed. Identifiers that exist for compatibility (`supabase_migrations`, `supabase_functions`, `SUPABASE_URL`, the `supabase/` folder) keep their names.
- The CLI reads `supabase/` (`config.toml`, `migrations/`, `functions/`, `seed.sql`) and never writes inside it, except the one new file `migration new` and `functions new` are asked to create. Its own state lives in `.selfbase/`, which ignores itself (`.selfbase/.gitignore` containing `*`); no tracked file of the app repository is touched. Unknown `config.toml` keys and sections are ignored, never an error.
- CorteQS repository (`D:\Dev\corteqsemir`, worktree `D:\Dev\corteqsemir-wt\selfbase`): no push, no PR, migration files never edited, `scripts/ops/*` never run. Its Supabase project ref is never written into this repository.
- The repository is public: never a server IP, hostname or secret in it. Use `<ip>` and `<BASE>`.
- Secrets are never printed, logged, committed, put in job payloads, audit rows or error messages. Function secret values are write-only: no API, CLI or Studio path returns one (a sha256 digest stands in, as Supabase does).
- `/v1` routes name the `operationId` they implement and match path, method and field names of `docs/reference/management-api.json` (`control/test/openapi.test.ts` checks it). Anything else goes under `/platform`.
- Certificates: this wave requests **zero** new hostnames. Server proofs use the fixed test host `sb-test.<BASE>` (pool `test`, one project at a time).
- Shared-host rule (spec 5) as in wave 1. New in this wave: published host ports, only from `DB_PORT_RANGE` (`54000-54999`), only for a project whose external access an administrator switched on.
- The provisioner still never sets `Privileged`, `CapAdd`, host namespaces, devices or bind mounts beyond the backup directory. `PortBindings` are allowed only as Task 12 defines. No runtime dependency beyond Node's standard library. Line cap: 1100 (D-3).
- Job types stay the fixed enum of AC-11. This wave adds none.
- Platform migrations `0004`+ are safe to run twice and never drop user data. Numbers are assigned here: `0004-migration-history`, `0005-net-complete`, `0006-vault-encryption`, `0007-graphql-queues-webhooks`, `0008-pooler-auth`. Control migrations: `0008-functions-created-at` (Task 14), `0009-external-db` (Task 15); `0004`–`0007` were taken by wave 1's fix wave.
- Language (owner, 2026-11-23): English is the product's main language, Turkish the second locale. Every new Studio string is a `t()` key present in **both** `studio/src/i18n/en.ts` and `tr.ts`; no literal user-facing string in a component. - Each code task: failing test → implementation → passing test → commit. Integration tests run against real Postgres / real Docker / real Deno, no mocks of them.
- A shortcut with a known limit carries a `shortcut: <limit>, <when to upgrade>` comment.

## Review Focus

1. **A migration that ends its own transaction or fails half-way.** A file with a hidden `COMMIT`, or one whose third statement fails, leaves no history row, `db push` stops there and runs no later file, and the answer says which file and line. → Task 6.
2. **Hostile paths in a function deploy.** File names `../x`, `/etc/x`, `a\..\b`, a NUL byte, slug `_shared`, `..` or 200 characters never write outside `<slug>/<version>/` and never replace `manifest.json`. → Task 9.
3. **A function secret named like a platform secret.** Setting function secrets `POSTGRES_PASSWORD`, `JWT_SECRET` or `SMTP_PASS` leaves the project's own secrets untouched and the containers' platform env unchanged; no secret value appears in any response, audit row, job payload or log. → Task 14.
4. **Redeploy and broken functions under load.** A redeploy while requests are in flight finishes them on the old version; a function that throws at import, exits the process or runs out of memory answers 5xx for itself only; other functions and the host keep serving. → Task 10.
5. **The published database port without TLS, or a port that is taken.** `sslmode=disable` from outside the project network is refused on both ports; a port clash never leaves `db` stopped; switching external access off closes both ports. → Tasks 11, 12, 15.

## Decisions

Open points and contradictions, decided here with the reason. The controller can overturn any of them before the task that implements it.

| # | Issue | Decision and reason |
|---|---|---|
| D-1 | Spec 7.9: "against a linked project the diff runs server-side as a provisioner job". A linked project has one database; the other side of the diff (the developer's local schema) is on the developer's machine. | `db diff --linked` and `db pull` fetch a schema-only dump of the linked project through the API (`db dump` path) and run migra **locally** against it. Reason: the server-side variant needs developer SQL loaded into a scratch database in the production cluster or a second db container under admission, plus migra on the shared server. The `migra-diff` job type stays `501` until wave 4, where both sides (branch and parent) are server-side. |
| D-2 | `v1-apply-a-migration` takes `{query, name}` and no version; `db push` must record the file's own version. | `/v1` POST applies with a server-generated UTC version. The CLI uses `PUT /platform/projects/{ref}/migrations/{version}` (SQL as the body). `/v1` GET lists both. |
| D-3 | Spec 7.5 targets a provisioner under 1000 lines; it is at 975 and this wave adds function env, the worker cap and published ports. | Cap 1100 for wave 2, count stated in each provisioner commit. Reason: the alternative is moving validation out of the one component whose job is validation. |
| D-4 | AC-23 fixes Deno Workers; Deno has no per-worker import map, but 8.5 requires each function's `deno.json` to be honoured. | `fn` builds one import map with a `scopes` entry per deployed function at start. A deploy that changes any function's imports makes `fn` exit after draining; the restart policy brings it back (~2 s) with the new map. Code-only redeploys never restart it. Works with the control plane down. |
| D-5 | How a Worker receives requests is open. | Each Worker listens on a loopback port and the host proxies with `fetch`. Reason: streaming bodies work unchanged. `shortcut:` no WebSocket upgrade into a function, until a function needs one. |
| D-6 | The multipart deploy shape names files; the layout on the volume must keep `../_shared` imports working. | File names are POSIX paths relative to `supabase/` (`functions/<slug>/index.ts`, `functions/_shared/x.ts`); a version directory holds that tree. `functions/{slug}/body` answers the same multipart shape (files + `metadata`), not an eszip. *(verify, upstream)* against the real CLI at the real-CLI step, not now. |
| D-7 | 7.8 lists config groups; core has no realtime or Postgres settings to store yet. | Wave 2 ships `postgrest`, `config/auth` (the fields core has today, table in Task 13) and `config/storage` (`fileSizeLimit`). `config/database/postgres`, `config/database/pooler` (PATCH) and `config/realtime` come with the waves that add their settings. A PATCH naming a field we do not store answers 400 `not_supported` with the field name, never a silent ignore. |
| D-8 | 8.6 lists database object screens without saying how much editing they do. | Functions, triggers, enumerated types, indexes and roles are lists with "new … in the SQL editor" (a prefilled template). Extensions, publications, cron, queues, webhooks, vault and migrations have real actions. Reason: forms for arbitrary DDL duplicate the SQL editor. |
| D-9 | "pgmq (SQL-only install)". | The db image copies `pgmq.control` and its SQL files from the pinned upstream release into the extension directory, so `create extension pgmq` works as existing migrations expect. No compiled code. |
| D-10 | Vault: "real encryption", key in a file outside the data directory. | pgcrypto `pgp_sym_encrypt` (AES-256) with the key read by a security-definer function from `/run/selfbase/vault.key`; table keeps `supabase_vault`'s column list so dumps restore. A project without `VAULT_KEY` does not start. |
| D-11 | 8.9 gives each project a server certificate; when it is used is open. | Every project's `db` and `pooler` always run with TLS (control issues the certificate at the next apply; plain compose self-signs). The hba files require TLS from any peer outside the project /27 **and from its gateway address**, which is how a connection through a published port can appear. |
| D-12 | CC-3: the provisioner "checks the port is free on the host first"; it cannot see host sockets. | It refuses a port another container already publishes (from `GET /containers/json`), and if the start still fails on the port it recreates the service without ports at once and answers 409 `port_in_use`; control retries with the next pair. |
| D-13 | AC-15: "shipped as one bundled file (`npx selfbase`)"; `selfbase start` builds images from the repository (CC-1). | The bundle is `cli/dist/selfbase.mjs`, attached to the GitHub release. Publishing to npm is an **Owner step**, not part of this wave. `selfbase start` needs a selfbase checkout (`--selfbase-dir`, `SELFBASE_DIR`, or the bundle's own repository). |
| D-14 | Local mode (7.6) with "one code path" for Studio. | Local control runs with its own `control-db`, a static provisioner (`localProvisioner`), no jobs, no reconcile; job-backed routes answer 409 `local_mode`. It serves only requests whose `Host` is `127.0.0.1` or `localhost`. |
| D-15 | `sync.mjs` also re-armed v1 realtime triggers and reloaded PostgREST after a run. | core's migration apply does both after each successful apply, until wave 3 replaces the triggers. |
| D-16 | Migration files without a 14-digit version (`sync.mjs` applied them by name). | As the supabase CLI: they are not migrations; `migration list` and `db push` name them as skipped. Their old records stay in `selfbase.applied_migrations`, untouched. |
| D-17 | Memory per function is uncapped inside `fn` (known difference, 8.5). | Live Workers are capped per size (`fn.max_workers` in `sizes.json`: micro 4, small 8, medium 16); the least recently used idle Worker is ended first; with none idle the request answers 503 `Retry-After: 1`. |
| D-18 | migra's maintenance status (spec 12). | Task 19 first builds our own image from the pinned PyPI release and runs it against Postgres 17 with a table, a policy, a function and a view. If it fails, the task stops and goes to the controller; nothing else in the wave depends on migra. |
| D-19 | Function secrets share `control.project_secrets (project_id, name)` with platform secrets. | They are stored as `fn:<NAME>`, kind `function`. Reason: Review Focus 3. |
